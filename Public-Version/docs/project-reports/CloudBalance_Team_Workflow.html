1. How one request travels

flowchart LR
    C["Client: web page or laptop-1/2/3 script"] --> N["Nginx :80"]
    N --> F["FastAPI controller"]
    F --> S{"Scheduler mode"}
    S -->|"milp"| M["MILP picks least-loaded worker"]
    S -->|"round_robin"| R["Next worker in cycle"]
    M --> W["Worker 1 / 2 / 3"]
    R --> W
    W --> F
    F --> L[("CSV: test_log.csv")]
    F --> C

Only the scheduler box differs between the two tests. Everything else is the same code path.

2. The Round Robin bug fix (dispatch logic)

flowchart TD
    T["Task arrives"] --> Q{"Read mode once: task.mode"}
    Q -->|"round_robin"| R["n = Redis INCR rr_counter
worker = W[(n-1) mod 3]
dispatch_seq = n"]
    Q -->|"milp"| B["Micro-batch buffer"] --> O["OR-Tools MILP solve
uses in-flight counts"]
    R --> S["Send to worker"]
    O --> S
    S --> G["Log scheduler_used + dispatch_seq"]
  • Round Robin never enters the batch loop or the solver, so MILP can no longer decide in RR mode.
  • One global atomic counter means order is w1, w2, w3, w1... no matter which laptop sent the task.
  • Mode is locked while a test is running; counters reset at test start.

3. Test lifecycle

stateDiagram-v2
    [*] --> idle
    idle --> armed: Admin Start (mode, duration, seed)
    armed --> running: start_at reached (5s sync)
    running --> draining: duration ends or Stop
    draining --> idle: summary row written

Run MILP test → rest about 3 minutes → run Round Robin test with identical parameters. Laptops poll /test/status, wait for armed, then all start together at start_at.
