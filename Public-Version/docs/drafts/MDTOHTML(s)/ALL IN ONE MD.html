C. Why Redis with a 10-Second TTL (SETEX cluster:worker:{id} 10)?

In ClusterStateService.update_telemetry()[cite: 2]:

key = self.worker_key(telemetry.worker_id)  # "cluster:worker:worker-1"
payload = telemetry.model_dump_json()
await self._redis.setex(key, self._ttl_seconds, payload)  # TTL = 10 seconds
  • O(1) In-Memory Speed: The micro-batcher runs every 200ms[cite: 2]. Reading 3 worker keys from Redis takes < 1 ms, whereas querying disk-based databases on every batch would bottleneck the scheduler[cite: 2].
  • Self-Healing Passive Health Check: Each worker refreshes its key every 1.5–2.0 seconds, resetting its TTL back to 10 seconds[cite: 2]. If a worker VM crashes or loses network connectivity, its key automatically vanishes from Redis after 10 seconds—achieving automatic failover with zero manual intervention[cite: 2].

D. Worker Health Status Thresholds (compute_worker_status)

In backend/app/models/schemas.py[cite: 2]:

  • HEALTHY (Green): cpu_percent < 60% AND memory_percent < 70%[cite: 2]
  • MODERATE (Amber): cpu_percent in 60–84% OR memory_percent in 70–89%[cite: 2]
  • CRITICAL (Red): cpu_percent >= 85% OR memory_percent >= 90%[cite: 2]

5. Top Viva Questions & Answers for Member 1

  1. Q: Why use Redis for worker telemetry instead of storing it in MongoDB?
    A: Telemetry is high-frequency, ephemeral state updated every 1.5–2 seconds per worker and read every 200ms by the scheduler[cite: 2]. Redis stores keys in RAM with sub-millisecond latency and supports native key expiration (SETEX with 10s TTL), so stale/dead workers automatically disappear without background cleanup jobs[cite: 2].
  2. Q: What happens if a Worker VM crashes mid-execution?
    A: Two mechanisms protect the cluster: (a) if an HTTP dispatch to :8001/execute fails, DispatcherService immediately calls cluster_state.evict_worker(worker_id) (DELETE cluster:worker:{id}); (b) even if no task is currently dispatching, the dead worker stops sending heartbeats and its Redis key expires after 10 seconds[cite: 2].
  3. Q: How does the system run locally on a laptop if Redis Server isn't installed?
    A: DualRedisClient (backend/app/core/redis_client.py) pings redis://localhost:6379/0 on startup[cite: 2]. If unreachable, it seamlessly falls back to InMemoryTTLStore, which implements the exact same async setex, get, keys, ttl, and delete interface using time.monotonic() expiration timestamps[cite: 2].

B. Poisson Arrival Process & Superposition (traffic/poisson_generator.py)

  • Inter-Arrival Formula: Given arrival rate λ (tasks/sec) and U ~ Uniform(0, 1), the inter-arrival time is: dt = -ln(1 - U) / λ[cite: 3].
  • Superposition Property: When K client laptops independently generate Poisson streams with rates λ1, λ2, ... λK, the combined arrival stream at the Controller's single entry point is a Poisson process with total rate: Λtotal = Σ λk[cite: 3].

C. Google OR-Tools MILP Formulation (backend/app/schedulers/ortools_milp.py)

Given a micro-batch of N tasks (i ∈ {0, ..., N-1}) and M active workers (j ∈ {0, ..., M-1})[cite: 3]:

  1. Decision Variables[cite: 3]:
    • Binary assignment variable Xi,j ∈ {0, 1}, where Xi,j = 1 iff task i is assigned to worker j[cite: 3].
    • Continuous peak CPU variable Z ∈ [0, 100][cite: 3].
    • Continuous peak memory percentage variable Mpeak ∈ [0, 100][cite: 3].
  2. Base Load (Telemetry + Decaying In-Flight Reservations)[cite: 3]:
    • BaseCPUj = TelemetryCPUj + InFlightCPUj[cite: 3]
    • BaseMemj = TelemetryMemj + InFlightMemj[cite: 3]
  3. Hard Constraints[cite: 3]:
    • Single Assignment: Σj Xi,j = 1 for all i[cite: 3]
    • CPU Safety Cap (≤ 85%): BaseCPUj + Σi cpui * Xi,j ≤ 85.0 for all j[cite: 3]
    • RAM Safety Cap (≤ 90% of Total RAM): BaseMemj + Σi memi * Xi,j ≤ 0.90 * TotalMemj for all j[cite: 3]
    • Min-Max Peak Linearization: ProjectedCPUj ≤ Z and ProjectedMemPctj ≤ Mpeak for all j[cite: 3]
  4. Objective Function: min (Z + 0.001 * Mpeak)[cite: 3]. This minimizes the highest CPU load across all workers while using memory utilization percentage as a tie-breaker (steering 1024 MB MEMORY_INTENSIVE tasks toward the 8 GB worker-3 when CPU loads are tied)[cite: 3].
  5. Degraded Fallback (_degraded_fallback): If a massive burst makes the 85% CPU / 90% RAM caps mathematically INFEASIBLE, the scheduler does not drop tasks; it switches to greedy lowest-projected-load routing, sets degraded=True, and emits a live warning banner to the Dashboard[cite: 3].

5. Top Viva Questions & Answers for Member 2

  1. Q: Why use Mixed-Integer Linear Programming (MILP) instead of Least Connections?
    A: Least Connections only counts how many tasks a server has, treating a 10% CPU query and a 35% CPU / 1 GB RAM job as identical (1 connection)[cite: 3]. Moreover, when a batch of 10 tasks arrives, greedy heuristics assign one by one without global lookahead, whereas MILP solves the joint combinatorial placement across both CPU and RAM constraints in ~6 milliseconds[cite: 3].
  2. Q: Why do we need InFlightTracker (backend/app/schedulers/base.py)?
    A: Worker psutil telemetry arrives every 1.5–2.0 seconds, whereas micro-batches run every 200ms[cite: 3]. Without in-flight reservations, 5 consecutive batches within 1 second would all read the same old telemetry and dump every task onto the same idle server[cite: 3]. InFlightTracker reserves the task's CPU and RAM immediately upon scheduling and releases it as soon as worker telemetry absorbs the active task or completes execution[cite: 3].
