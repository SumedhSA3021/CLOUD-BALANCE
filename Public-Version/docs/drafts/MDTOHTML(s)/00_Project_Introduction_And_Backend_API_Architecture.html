CloudBalance — Project Introduction, Member-Wise Workload Distribution & Backend API Architecture

1. Project Introduction

CloudBalance is an adaptive, multi-resource cloud load balancer designed to overcome the core limitation of traditional cloud load-balancing heuristics (such as Round Robin and Least Connections)[cite: 1]. Traditional load balancers route incoming requests blindly without considering[cite: 1]:

  1. Multi-dimensional task resource costs (a CPU-heavy AI inference job vs. a RAM-heavy in-memory graph query vs. a lightweight database lookup)[cite: 1].
  2. Live heterogeneous server utilization (real-time CPU percentage, physical RAM usage, and in-flight queued load across worker VMs of different capacities)[cite: 1].

CloudBalance solves this through a four-stage closed-loop feedback architecture (Monitor -> Optimize -> Dispatch -> Visualize) exposed behind a Single Public Entry Point (:8000)[cite: 1]:

  • Clients (3+ Laptops & Mobile Devices) only know the Controller's single URL (http://<Controller-IP>:8000)[cite: 1]. Clients never declare raw CPU or RAM numbers; they interact with the Client Portal (/client) or run the cb-traffic CLI and send only { "client_id": "...", "task_type": "..." }[cite: 1].
  • The FastAPI Controller (:8000) validates requests, applies rate-limiting and queue backpressure (HTTP 429), and maps each task_type to its authoritative server-side resource profile (cpu_demand_pct, mem_demand_mb, duration_sec, matrix_dim)[cite: 1]. It collects tasks into 200ms micro-batches, reads live worker telemetry from Redis (cluster:worker:*), and asks the Google OR-Tools Mixed-Integer Linear Programming (MILP) Scheduler for the globally optimal task-to-worker assignment matrix Xij[cite: 1].
  • Private Internal Worker VMs (:8001, :8002, :8003) have no public IP exposure[cite: 1]. They receive dispatched tasks over the internal network (POST /execute), execute genuine NumPy (np.dot) matrix multiplications, and run a psutil Telemetry Agent that reports real-time CPU, RAM, load average, and active task counts back to the Controller every 1.5–2.0 seconds (SETEX cluster:worker:{id} 10)[cite: 1].
  • Dual-Database Persistence & Live WebSocket Streaming: Ephemeral live state is stored in Redis (with 10s worker TTL for automatic dead-node eviction)[cite: 1]. Historical assignments and benchmark runs are stored in MongoDB / SQLite[cite: 1]. A 1.5s WebSocket Broadcaster (/ws) pushes live CLUSTER_SNAPSHOT frames to the React 18 Ops Dashboard (/) and Client Portal (/client)[cite: 1].

3. How the API Calls Work Across the Whole System (Step-by-Step Lifecycle)

Every numbered step below corresponds directly to [1]–[12] in the architecture diagram above[cite: 1]:

Step [1] — Client Sends Task Request to Single Public Entry Point (:8000)

  • Caller: Laptop/Mobile Browser on /client (frontend/src/lib/api.ts) or cb-traffic CLI (traffic/cli.py)[cite: 1].
  • Endpoint: POST /api/v1/tasks (with automatic idempotent fallback GET /api/v1/tasks/submit?client_id=...&task_type=... for mobile hotspots)[cite: 1].
  • Request Payload[cite: 1]: 
    {
  "client_id": "laptop-alpha",
  "task_type": "CPU_INTENSIVE"
}
  • Guardrails Checked (backend/app/api/tasks.py)[cite: 1]:
    1. verify_api_key checks X-API-Key when CB_REQUIRE_API_KEY=true[cite: 1].
    2. TokenBucketRateLimiter checks per-second burst limits (HTTP 429 if exceeded)[cite: 1].
    3. Queue depth check: if batcher.queue_depth >= max_queue_depth, immediately returns HTTP 429 Too Many Requests (backpressure)[cite: 1].

Step [2] — Server-Side Resource Profile Resolution

  • Module: backend/app/core/profiles.py (resolve_task_profile) & Task.from_request() (backend/app/models/schemas.py)[cite: 1].
  • What Happens: Clients never specify CPU% or RAM MB[cite: 1]. The Controller looks up task_type in its authoritative table[cite: 1]:
    • CPU_INTENSIVE → 35.0% CPU, 256.0 MB RAM, 2400×2400 matrix, 4.0s duration[cite: 1]
    • MEMORY_INTENSIVE → 15.0% CPU, 1024.0 MB RAM, 4500×4500 matrix, 5.0s duration[cite: 1]
    • BALANCED_COMPUTE → 25.0% CPU, 512.0 MB RAM, 2000×2000 matrix, 3.0s duration[cite: 1]
    • LIGHTWEIGHT_QUERY → 10.0% CPU, 128.0 MB RAM, 1000×1000 matrix, 1.5s duration[cite: 1]

Step [3] — Enqueue into Micro-Batcher (200ms Window or 20 Tasks)

  • Module: backend/app/services/batcher.py (MicroBatcherService.enqueue)[cite: 1].
  • What Happens:
    • The enriched Task is appended to an async queue (collections.deque), and client_stats.record_enqueue() updates per-client arrival rates (req/s)[cite: 1].
    • The task is also cached in Redis (SETEX cluster:task:{task_id} 60 <json>)[cite: 1].
    • The Controller immediately returns HTTP 202 Accepted to the client with the generated task_id and queue_depth[cite: 1].

Step [4] & [9] — Micro-Batcher Reads Live Workers from Redis & Calls Scheduler

  • Modules: ClusterStateService.get_active_workers() (backend/app/services/cluster_state.py) → ORToolsMILPScheduler.assign() (backend/app/schedulers/ortools_milp.py)[cite: 1].
  • What Happens:
    • Every 200ms (or immediately when 20 tasks accumulate), flush_one_batch() reads all non-expired cluster:worker:* keys from Redis ([9])[cite: 1].
    • It passes (batch_tasks, active_workers) to the active scheduler (ortools_milp, round_robin, or least_connections)[cite: 1].
    • OR-Tools MILP combines each worker's Redis telemetry with InFlightTracker reservations, solves the binary assignment problem (min Z + 0.001 M subject to ∑j Xij=1, CPUj ≤ 85%, RAMj ≤ 90%), registers new in-flight reservations, and returns BatchAssignmentResult(assignments, meta)[cite: 1].

Step [5] & [6] — Internal HTTP Dispatch to Worker Executor (:8001–8003) & Automatic Failover

  • Module: backend/app/services/dispatcher.py (DispatcherService.dispatch_task)[cite: 1].
  • Endpoint Called (Internal RPC): POST http://<worker_internal_ip>:<port>/execute (e.g., http://127.0.0.1:8001/execute locally or http://10.128.0.11:8001/execute on GCP VPC)[cite: 1].
  • Request Payload[cite: 1]: 
    {
  "task_id": "tsk-a53ed9071d",
  "duration_sec": 4.0,
  "matrix_dim": 2400,
  "cpu_demand_pct": 35.0,
  "mem_demand_mb": 256.0
}
  • Retries & Automatic Re-Solve Failover:
    • Uses tenacity.AsyncRetrying (stop_after_attempt, timeout)[cite: 1].
    • If a worker VM crashes or times out, DispatcherService immediately releases its in-flight reservation, evicts cluster:worker:{failed_id} from Redis, re-runs the scheduler excluding the failed worker, and dispatches the task to the newly chosen healthy worker VM[cite: 1].

Step [7] & [8] — Worker Executes Real np.dot & Reports psutil Telemetry to Redis

  • Modules: worker/executor.py (execute_workload) & worker/agent.py (WorkerTelemetryAgent) → POST /api/v1/telemetry (backend/app/api/telemetry.py)[cite: 1].
  • What Happens:
    • The Worker increments its active task counters, immediately pushes a live telemetry update to POST /api/v1/telemetry, and runs real NumPy matrix multiplications (np.dot(a, b)) in a worker thread[cite: 1].
    • Every 1.5s–2.0s (and upon task start/completion), the worker agent samples psutil.cpu_percent(), psutil.virtual_memory(), os.getloadavg(), and active_task_count and sends POST /api/v1/telemetry[cite: 1].
    • The Controller executes SETEX cluster:worker:{worker_id} 10 <json> in Redis ([8])[cite: 1]. If a worker dies and stops sending heartbeats, its Redis key automatically expires after 10 seconds[cite: 1].

Step [10] — Persist Assignment & Completion Status to MongoDB / SQLite

  • Modules: backend/app/services/history.py (HistoryService) & backend/app/core/mongo_client.py (DualMongoClient)[cite: 1].
  • What Happens:
    • When a task is scheduled, an Assignment record (status="ASSIGNED") is saved[cite: 1].
    • When POST /execute returns 200 OK with execution_ms, HistoryService updates the record to status="COMPLETED" with the real execution time in both MongoDB/SQLite (assignments collection/table) and Redis (cluster:assignment:{task_id})[cite: 1].

Step [11] & [12] — Real-Time WebSocket Broadcast (/ws) & Runtime Control APIs

  • Modules: backend/app/services/broadcaster.py (WebSocketBroadcaster), backend/app/api/websocket.py, backend/app/api/control.py[cite: 1].
  • What Happens:
    • Every 1.5s (and immediately on any control action), WebSocketBroadcaster builds a ClusterSnapshot combining live worker snapshots (workers), the last 20 assignments (recent_assignments), per-laptop metrics (clients), queue_depth, active_scheduler, and avg_solver_latency_ms, and broadcasts it over WS /ws ([11])[cite: 1].
    • Operators on the Dashboard can hot-swap schedulers (POST /api/v1/control/scheduler), inject burst spikes (POST /api/v1/control/traffic), or simulate worker crashes/revivals (POST /api/v1/control/workers/{id}/kill and /revive) ([12])[cite: 1].
